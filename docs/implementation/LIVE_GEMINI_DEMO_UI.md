# Live Gemini Demo UI (Phase 9.2)

**Date**: 2026-09-26
**Endpoint Integration**: `POST /api/demo/scenarios/live/water-convergence`

## 1. Overview
The Live-AI Demo UI integrates the single-village controlled live Gemini demonstration into the Civic Intelligence dashboard. It provides policymakers with a safe, bounded way to witness real-time AI interpretation without exposing internal API keys, uncontrolled language models, or arbitrary prompts to the browser.

## 2. Browser/Server Boundary
- **Browser Role**: The frontend acts strictly as a dumb client. It triggers the demonstration and renders the result.
- **Server Role**: The backend controls the scenario configuration, synthetic signal generation, real LGD village mapping, and Gemini orchestration.
- The browser **cannot** supply a scenario ID, custom prompt, model, village code, or any other execution parameter.

## 3. One-Signal & One-Request Semantics
- The UI exposes a single action: **"Run Live Gemini Demo"**.
- This action fires exactly one HTTP request to the backend.
- The backend performs exactly one synthetic signal generation and exactly one Gemini inference call (`gemini-3.1-flash-lite`).
- The UI visibly reflects this controlled state by displaying "Gemini requests: 1" when the backend confirms it.
- **No Client-Side Retries**: The frontend deliberately does not implement polling, duplicate firing, or automatic error retries. Once a request fails, the user must manually trigger it again.

## 4. UI Distinction: Live vs Mock
The demo panel is strictly separated into two distinct visual areas:
1. **LIVE GEMINI DEMO**: Clearly labeled as a "SINGLE REQUEST DEMO" using the Live Gemini AI.
2. **Deterministic Mock Demo**: The existing offline validation demo.
A user cannot confuse which mode they are running.

## 5. Synthetic vs Real Evidence
The UI maintains a strict visual and semantic distinction between evidence types:
- **Synthetic Citizen Signal**: Visually tagged as `SYNTHETIC DEMO SIGNAL`. It is never misrepresented as actual, verified citizen feedback.
- **Real Public Evidence**: Visually tagged as `REAL / OFFICIAL JJM/LGD`. This represents the actual infrastructure gap mapping.

## 6. Pipeline Visualization & Boundaries
The live demo renders a compact pipeline flow:
Synthetic Citizen Signal → LIVE GEMINI → Civic Need → Citizen Demand → Unmet Demand → Convergence → Deterministic Priority → Evidence Ledger.

**Architectural Boundary:**
The UI explicitly informs the user that the **Priority Score is calculated deterministically from versioned evidence**, and is NOT generated by Gemini.

## 7. Context Integration & Transitions
- **Selected Village Integration**: Upon a successful run, the returned `lgd_village_code` is seamlessly synchronized into the global `VillageContext`.
- **Priority/Evidence Transitions**: If the live pipeline completes up to the Priority/Ledger stage, an "Inspect Evidence" action is provided. This smoothly scrolls the user down to the existing unified policymaker workspace (Hotspot Map / Priority Decision Panel) focused on that exact village.

## 8. Feature Flag & Failure Handling
- **Disabled State**: If the backend feature flag `DEMO_LIVE_GEMINI_ENABLED` is disabled, the API returns a `403 Forbidden` (`LIVE_GEMINI_DEMO_DISABLED`). The UI safely degrades, displaying: "Live Gemini demonstration is currently disabled."
- **Safe Errors**: In the event of backend or pipeline errors, the UI displays controlled user-facing error messages (e.g., "Pipeline Error at stage: Convergence") without leaking stack traces or internal mechanics.

## 9. Security Boundary Validation
- **No Sensitive Data Leaks**: The frontend never receives or displays raw API keys, internal pseudonyms, or full language model thought signatures.
- **Validation**: 30+ dedicated frontend tests enforce this contract, ensuring loading states lock execution, arbitrary parameters cannot be injected, and rendering logic honors the semantic boundary between Gemini and deterministic execution.
