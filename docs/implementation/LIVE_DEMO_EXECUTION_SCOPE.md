# Live Demo Execution Scope Boundary (Phase 9.1C)

**Date**: 2026-09-26
**Endpoint**: `POST /api/demo/scenarios/live/water-convergence`

## Problem Context
During the 9.1B validation phase, the live smoke test demonstrated that while the Gemini API interaction was successfully restricted to 1 call, the downstream deterministic pipeline was evaluating the entire derived statewide dataset (over 30,000 public evidence records) for the sake of one demonstration signal. This was an unintended performance bottleneck.

## Solution: Targeted Execution Boundary
To solve this, we introduced the `DemoExecutionScope` boundary which targets the pipeline execution to only the single LGD village and canonical need generated by the simulated signal.

### Exact Scope Boundary
The orchestrator now extracts the `lgd_village_code` and `canonical_need_type` from the synthesized demand evidence during a live demonstration.
This explicit scope is propagated downwards to:
- `UnmetDemandAssessmentEngine`
- `ConvergenceOpportunityEngine`
- `ConvergencePriorityEngine`

### Public Evidence Selection
When evaluating unmet demand, the engine will only read and process the public evidence from `AnalyticsRepository` that matches the targeted village code, skipping the rest.

### Downstream Record Bounds
Because the engines only evaluate the targeted village, they generate only exactly 1 relevant downstream logical output for each stage:
- 1 Unmet Demand Assessment
- 1 Convergence Opportunity
- 1 Priority Assessment
- 1 Evidence Ledger Entry

### Idempotency and Statewide Integrity
Instead of overwriting the entire derived artifact with just the single demonstration result (which would destroy the other 29,999 records), the local repositories now use an `upsert_*` methodology when bounded execution is triggered. This maintains local statewide dataset integrity, while safely appending or updating the results for the targeted village.

## Security
No changes to API contracts, BigQuery, or Gemini boundaries. The execution scope remains server-side only; the browser cannot supply an arbitrary LGD village or scope parameter. The offline simulator chooses the village deterministically exactly as it did before.

## Performance Expectations
Execution time for a live demo API request reduces from O(N) (scanning and recalculating 30,000 villages) to O(k), where k is the targeted village scope. Performance is virtually instantaneous once the single Gemini inference resolves.
